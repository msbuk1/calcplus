# 29 — Producer matrix: what the seven writers emit and what the reader must tolerate

Status: research complete
Date: 2026-11-18
Ticket: milestone 6, slice 6E (producers and hostile input) plus the fixture-corpus work for the whole milestone
Method: primary producer documentation and specification notes (Microsoft Open XML documentation, European Computer Manufacturers Association standard ECMA-376, SheetJS write-options reference, openpyxl stable documentation, LibreOffice help), the prior calcplus research notes, and published interoperability reports. No local fixture experiments were run for this note; every claim that needs a captured file is marked UNVERIFIED. Vendor marketing claims are marked as vendor claims, not facts.

## TL;DR

The seven named producers fall into three groups. Excel 365 and Excel 2019 write the reference form: a shared-string table, cached formula values, full style tables, and complete chart, drawing, macro, pivot, and external-link parts. LibreOffice and Google Sheets write valid but lossy Office Open XML (OOXML): they preserve most cell content while dropping or downgrading charts, pivots, macros, and newer Excel constructs. The three libraries are the least faithful: openpyxl writes shared strings in normal mode but inline strings in write-only mode and drops charts and images from files it did not itself create; SheetJS Community Edition writes inline strings by default and drops styles, validation, conditional formatting, charts, and external links; xlsx-populate preserves unknown parts byte-for-byte but deliberately writes no cached formula values.

The reader must therefore tolerate, at minimum: missing `dimension` records, cells with no `t` (type) attribute, inline strings alongside shared strings, formula-string `t="str"` cells from SheetJS, dangling shared-string entries, sheet-name quoting with doubled single quotes, both date systems, XML (Extensible Markup Language) whitespace and pretty-printing differences, namespace prefix variation, and relationship identifier ordering differences. The existing 24-fixture list is missing producer-origin coverage: F22 names only four producers and no fixture proves the file came from a real producer. The recommendation is to add three producer-output fixtures (openpyxl, SheetJS, xlsx-populate), three real-producer fixtures (LibreOffice-saved, Google Sheets-exported, Excel 365 with 365-only constructs), and two quirk fixtures (missing dimension, quoted sheet names), and to run four producers headless locally while keeping Excel 365, Excel 2019, and Google Sheets manual with stored goldens.

### 1.2 Date systems, workbooks, and calculation settings

- Excel writes the 1900 date system by default and sets the 1904 flag only for workbooks created in that mode; the flag lives in `workbook.xml` and the reader must honor it (F15 covers this; no new research needed).
- LibreOffice and Google Sheets exports of 1904 workbooks are UNVERIFIED: capture one 1904 workbook round-tripped through each to confirm the flag survives.
- `calcPr fullCalcOnLoad` handling differs by producer: Excel sets it when needed; library writers generally do not. The reader must never assume its absence means values are fresh.

### 1.3 What Excel 365 writes that Excel 2019 cannot

Dynamic arrays and spilling, `XLOOKUP` and related new functions, threaded comments with the persons part, and new chart types are 365-only. A 365 file opened in 2019 shows `#NAME?` for dynamic-array formulas while the rest of the sheet works [S16]. For the corpus this means one 365 fixture must contain a dynamic-array spill and an `XLOOKUP` with a cached value (proving the stale-versus-recalc rule in section 6.1 of the contract), and the 2019 check is manual open-and-observe, not an automated assertion.

## 2. Quirks the reader must tolerate

Rule from prior research that still holds: Excel does not strictly follow ECMA-376, so schema validation alone is insufficient; the corpus must be files actually produced by the producers [S17]. The table below states for each quirk which producers emit it and whether it needs tolerance code.

| # | Quirk | Producer or producers | Harmless, tolerance code, or genuine defect |
|---|---|---|---|
| Q1 | `dimension` record missing or stale (`A1:A1`, `A1`, or absent) | Third-party writers generally; Apache POI samples, some Pandas paths, and openpyxl write-only outputs are documented examples [S10]. Real Excel always writes a plausible dimension. | Needs tolerance code. Never size the grid from `dimension` alone: recompute used range from `sheetData` when the record is absent or disagrees with observed cells. openpyxl documents exactly this failure (`reset_dimensions` workaround) [S7]. Prior note 27 already directs recomputation rather than shifting [S18]. |
| Q2 | Cells with no `t` attribute | All producers, including Excel: a cell without `t` is a number by the schema type `ST_CellType` [S20], and the Open XML Software Development Kit makes the same default explicit [S20]. | Harmless if coded correctly: default to number. A reader that requires `t` is non-conformant. |
| Q3 | `t="str"` formula-string cells holding literal strings | SheetJS Community Edition writes literal strings this way [S17]. Excel uses `str` only for formula results. | Needs tolerance code: accept `str` as a displayable string on read. Do not reject and do not confuse with shared strings. |
| Q4 | Inline strings (`t="inlineStr"`) with no `sharedStrings.xml`, including the empty-string shape | openpyxl write-only mode (all strings) [S10]; LibreOffice reads them [S14b]; some third-party readers crash on the empty-string child shape [S10]. | Needs tolerance code: parse `is` runs inline, accept empty strings, never require a shared-string part to exist. |
| Q5 | Unused and dangling shared-string entries (index count disagreements, unreferenced items) | Excel after row deletes; any producer that appends without garbage-collecting. The contract already permits unused entries and mandates append-only tables [S19]. | Harmless by design: never renumber, never reject on `count` or `uniqueCount` mismatch; rebuild counts from usage on write. |
| Q6 | Sheet-name quoting and escaping (`'My Sheet'!$A$1`, doubled `''` for embedded quotes) | All producers whenever a name contains spaces, dots, or quotes; observed in real chart XML (`'5.Tiers.Hourly'!$F$19:$F$40`) and documented in the question-and-answer record [S12]. | Needs tolerance code: the reference parser must strip one optional qualifier, un-double `''`, and split on the last `!` outside quotes. Mis-parsing here breaks chart-series classification in note 27 [S18]. |
| Q7 | Whitespace and pretty-printing differences, `xml:space="preserve"` | All producers. Microsoft's own shared-string example relies on `xml:space="preserve"` to keep a significant single space [S22]. LibreOffice pretty-prints; Excel writes dense XML (Extensible Markup Language). | Needs tolerance code: preserve `xml:space`, never trim significant spaces, never hash parts for comparison without canonicalization. Directly relevant to the 1 megabyte per-node cap in note 28: pretty-printing inflates text nodes but stays orders of magnitude under the cap for in-envelope files (UNVERIFIED against LibreOffice and Google exports; spot-check during the matrix [S23]). |
| Q8 | Namespace prefix variation (`x:` versus default namespace, prefixed versus unprefixed `r:`) | All producers; the Transitional family is identified by namespace Uniform Resource Identifier, not prefix [S21]. | Needs tolerance code: resolve by Uniform Resource Identifier with a namespace-aware parser (`xmlns: true` posture from note 28 [S23]), never by literal prefix. One positive Strict-family (`purl.oclc.org`) root still rejects the whole file [S21][S23]. |
| Q9 | Relationship identifier ordering and gaps (`rId1`, `rId7`, non-sequential) | Any producer that appends or deletes parts; Open Packaging Conventions put no ordering requirement on identifiers. | Harmless: resolve by target, never by numeric order; never renumber on write (contract section 6, dirty-part rule [S19]). UNVERIFIED as a producer-specific claim: no source was found showing a named producer emitting non-sequential identifiers, so this row is defensive, not empirical. |
| Q10 | Number-format code variants meaning the same thing (`$#,##0.00` versus `\`$`#,##0.00`, date-token case differences) | ExcelJS normalizes `$#,##0.00` by dropping the quoting in prior testing [S17]; Excel itself accepts quoting variants. | Needs tolerance code in comparison only: compare formats semantically (per the number-format contract), never by string equality, and never rewrite the stored code on a clean read. |
| Q11 | Non-schema attributes a strict reader rejects (`level` on `col`) | SheetJS Community Edition emits `level` alongside `outlineLevel`; openpyxl rejects it, LibreOffice tolerates it [S17]. | Needs tolerance code: ignore unknown attributes on `col`, `row`, and `c`; never fail the open. Genuine defect on the writer's side, but rejection would turn a readable file into a Tier C refusal, which is worse. |
| Q12 | Stale `calcChain.xml`, stale chart caches (`numCache`, `strCache`), stale pivot caches | All producers between edits; Excel itself produces stale caches routinely. | Handled by existing decisions: delete `calcChain.xml` with `fullCalcOnLoad="1"` on formula change, leave chart caches byte-untouched and report stale, never refresh pivots [S18][S19]. No new tolerance code beyond what notes 27 and 28 specify. |
| Q13 | 1900 versus 1904 date base | Excel honors both; producer handling on export is UNVERIFIED for LibreOffice and Google Sheets (section 1.2). | Needs tolerance code already in the contract (F15): read the flag, apply the base, preserve it [S19]. |
| Q14 | Rich-text runs flattened to plain text | SheetJS Community Edition flattens runs on write [S17]; Calc and Sheets may normalize run boundaries. | Needs tolerance code on read (accept any run splitting as the same string) plus the contract's edit rule (editing warns and flattens) [S19]. F17 covers it; the matrix needs one run-heavy fixture from Excel to prove untouched runs survive. |

## 4. How to run the matrix: local versus manual

The project rule is fixed: no test or check runs on GitHub; all checks run on the maintainer's machine; Excel 365 verification is manual with stored goldens [S19]. The split below follows that rule.

### 4.1 Fully local (scripted, headless, re-runnable)

- **openpyxl, SheetJS, xlsx-populate generation and round-trip.** Pinned versions in a committed script (the contract already requires a committed generator script [S19]). Drive normal and write-only modes for openpyxl separately; drive SheetJS with and without `bookSST` to produce both the shared-string and inline-string variants; drive xlsx-populate for the missing-`<v>` variant. Assert part inventory, index stability, and repair-free open via LibreOffice plus the relationship verifier where installed [S19].
- **LibreOffice headless conversion and verification.** `soffice --headless --convert-to` is the documented batch path [S14]; the community cheat sheet records tested conversion invocations [S14]. Use it both to generate `libreoffice.xlsx` fixtures and as the automated repair-free oracle (Calc opens without error). Pin the LibreOffice version in the fixture log; prior research used 24.2.7.2 [S17].
- **Relationship and inventory checks.** Part presence, identical uncompressed bytes for Tier B parts, resolvable relationships, and dimension-versus-data agreement run as local scripts. These catch Q1, Q5, and Q9 without Excel.

### 4.2 Manual (maintainer machine, recorded, with stored goldens)

- **Excel 365 and Excel 2019 opens.** Manual by project rule [S19]. Record for each: application name and build, file hash before open, whether a repair prompt appeared, and visible fidelity of charts, pivots, comments, validation, and conditional formatting. Store the opened-and-resaved golden beside the fixture so later runs can diff without re-opening Excel.
- **Google Sheets export capture.** Manual download; no headless path exists. Record account-independent details only: export date, source sheet structure, and the export menu path used. Never store credentials or sheet links in the repo.
- **Repair-free criterion.** "Opens in Excel 365 without a repair prompt" [S19] can only be observed manually; the local LibreOffice check is a proxy, not a substitute. A fixture passes the matrix only after both the local script and the manual open succeed.

### 4.3 What the manual procedure must record to be reproducible

Producer name and exact version or build; source file hash; save or export settings (Strict versus Transitional, compatibility options, Calc filter options); step-by-step open or export clicks; repair-prompt outcome; and the resulting file hash. Without these five lines the fixture is another synthetic file with a real-sounding name.
