# Deleting a sheet is terminal: no undo entry, no archive

A sheet delete in calcplus follows the conformance oracle: Excel deletes sheets permanently, so calcplus does too. The command runs with a terminal history — its change set applies (the sheet removal plus the `#REF!` formula rewrites and defined-name rewrites), no inverse transaction is recorded, and both undo and redo stacks are cleared, because earlier transactions can no longer be replayed against a workbook that lost a sheet. Every delete asks first with the warning `Deleting "…" cannot be undone, and its data may be lost. Delete the sheet?`; cancelling the prompt leaves the model untouched. Sheet insert and sheet rename remain ordinary undoable transactions, so the only recourse for a mistaken delete is the one Excel offers: do not save, or use Save As to keep the original file.

**Considered options:** an undoable delete that archives the removed sheet in memory for as long as history holds the transaction (the spec's original promise that undo restores the sheet); an undoable delete backed by a persistent snapshot kept outside the log (restore would work after a save, but it is a second long-lived archive with its own memory bound and a document state that no longer matches the saved bytes); a terminal delete gated by a warning prompt with no archive (chosen).

**Why:** an archive-backed undo dies at save timing. Once the file is written without the deleted sheet, undo either silently becomes unavailable exactly when the user reaches for it — depending on whether, and when, they saved — or it restores a sheet the saved file does not contain, desynchronising the document from the disk. Both violate "no silent loss"; the archive's lifetime also cannot outlast the history bound (200 transactions or 64 MB) or a reload, so undo availability would be unpredictable. A terminal delete makes the warning truthful, the history honest and the file state permanent in the same direction Excel is permanent.

**Consequences:** the M4 gate is re-read: M4 exit criterion 3 in [milestones](../../.scratch/calcplus/spec/milestones.md) ("Multi-sheet insert/delete/rename and undo work") now means insert and rename are undoable while delete is confirmed-and-terminal. There is no delete → save → undo → save sequence that brings the sheet back: the stacks are cleared at the delete, a save permanently drops the worksheet part, its relationships and its defined names, and a later insert may reuse the part number only because the old part is gone. A save racing a delete is handled during the write await: `structuralVersion` is captured before the write and `markSaved` keeps the workbook dirty when a sheet command ran during the await (the deleted sheet is not in the saved bytes), `setDocument` updates functionally keyed on session identity and falls back to the first visible sheet when the active sheet was deleted, and the removed sheet's dirty markers are dropped rather than holding the document dirty forever. Guards hold at both layers: the command refuses a delete that would leave zero visible sheets (deleting a hidden sheet leaves the visible count alone), and the tab strip refuses to delete a hidden sheet or the last visible sheet before the prompt ever appears.

**Spec alignment:** the [feature matrix §5](../../.scratch/calcplus/spec/feature-matrix.md) row ("undo restores"), [command system](../../.scratch/calcplus/spec/command-system.md) §3's sheet-delete bullet and §9 criterion 8 ("Undo of a sheet delete restores…"), and M4 exit criterion 3 in [milestones](../../.scratch/calcplus/spec/milestones.md) still describe the old undoable delete. They are approved for update in a later spec pass; this ADR is the decision of record until that pass lands. The pass landed on 2026-11-22: M4 exit criterion 3, the feature matrix §5 row, and command system §3 and §9 criterion 8 now describe the confirmed-and-terminal delete.
